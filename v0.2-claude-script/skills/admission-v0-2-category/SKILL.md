# admission-noshell-v0-2 / admission-v0-2-category

# 业务分类单选

适用于本次定义中**选项是业务类别**的枚举键（如实际业务类别、所属行业、用工场景）。`combine.py plan` 对这类键打印 `CATEGORY_TASK` 任务卡：本次原文、会触发规则的选项、脚本找到的线索。编码一律取本次 enum，下文的中文选项名只说明含义。

分类值的含义是“申报的业务属于哪一类”，**不是“已核实违法”**：不需要外部核查结论；项目内容、交付要求把经营方式、计酬方式、作业地点写清楚了，就足以分类。

## 四步判定（每个分类键都走一遍，不跳步）

**第 1 步 写机制**（写进 set 依据的“机制：”后面）。只依据项目内容 A08、交付要求 A07，其次项目简介 A09、岗位名称 A13，用一句话回答四个问题：

1. 人员**实际做什么**（销售/推广/催缴/施工/下井/陪聊/开发…）；
2. 卖的或经手的**是什么**（理财产品/贷款/拍品/代币/药品/保险…）；
3. **怎么计酬**（按发展人数？按下级业绩跨层返佣？固定工资？）；
4. **在哪作业、有无危险源**（井下/高空/工地/危化品车间/办公室）。

企业名称、经营范围、开票类目只作辅助：不能用宽泛的“信息技术服务”“软件开发”盖过项目里写明的业务机制。

**第 2 步 按决策顺序选**。从上往下，第一个“机制成立”的层就是答案，层内选最直接说明核心机制的一项：

| 顺序 | 层 | 选项及判定要点（机制成立即选，不要求原文出现选项名） |
|---|---|---|
| 1 | 违法类 | **电信诈骗**：冒充客服/公检法、虚假退款、诱导转账、刷单返利诱骗。**网络赌博**：组织下注、投注、赌资结算、博彩推广。**色情服务**：色情内容或交易 |
| 2 | 擦边/灰产 | **擦边服务**：付费语音陪聊、情感陪伴、陪玩、暧昧聊天（本版规则把语音陪聊归此项；常规客服、语音技术开发不算）。**相关灰产**：刷单刷量、养号接码、买卖/出租账号、代收代付套现 |
| 3 | 传销类 | **拉人头返利**：报酬按直接/间接发展的人数计算，或交入门费、推荐返利。**多级分销**：多层团队、按下级业绩跨层返佣，但没有按人数计酬。两者都有时选拉人头返利 |
| 4 | 金融类 | **理财**：向个人推介理财/基金/资管产品、资产配置建议、跟进申购持仓（持牌、自称咨询都不排除）。**集资**：向公众招募出资、归集资金、高息回报。**网贷**：招揽借款人、贷款撮合/助贷。**典当**：收当估值、发当金、赎当。**拍卖**：征集拍品、组织竞拍。**催收**：电话/短信/上门催缴逾期欠款。**虚拟币**：代币推广、虚拟币买卖撮合 |
| 5 | 高危类 | **矿山井下**：下井、采掘、巷道掘进、出矿。**危化品生产**：危险化学品配制、反应、生产。**高空高危**：登高、外墙、塔架、吊篮作业。**建筑施工**：土建、安装、拆除、浇筑等工程施工。**建筑劳务**：向工地提供现场劳务人员（工种劳务，不承包工程） |
| 6 | 私域/微商 | **微商**：朋友圈卖货、代理囤货。**社媒私域**：私域社群运营成交。只有渠道特征、没有人数返利证据时不升级为传销类 |
| 7 | 兜底 | **一般业务**：业务内容可辨识，以上各层机制都不成立，且把握过半。业务内容空缺、不可读、来源冲突无法辨识时**不兜底**，skip 并写明缺口 |

层间重叠时（如“网贷平台的贷后催收”）以第 1 步“人员实际做什么”为准：员工做催缴 → 催收；员工做放贷撮合 → 网贷。

**第 3 步 反例自查**。下列情况是“提到了相关词，但人员不从事该业务”，不选该类别：

- 为金融机构**开发**理财/借贷/交易系统软件；反诈、禁赌、普法**宣传**；建筑**设计**、工程**造价咨询**；化工企业的**行政/财务**岗位；
- 原文是否定句：“不涉及催收”“严禁赌博内容”；
- 金融/医药等行业企业招**会场布置、现场引导**等确实不碰本行业业务的临时辅助岗位（保留行业提醒，按实际岗位分类）。

反过来，下面这些**不是**反例，不能借口跳过：合同泛称“软件服务”或另写“不按人数计酬、不设多层返利”而项目原文写明了该机制（列双方原文、记 conflicts，仍按项目原文选）；“临时/兼职/推广”的医药销售、主播带货、保险地推（岗位本身就在做本行业业务）；“尚未外部核实”。

**第 4 步 提交**。只交 `set`，依据里的条目就是映射，不必另写 map；set 落盘，后续 build 不必重提：

```
"set":{"<对象.属性>":["<选项编码>","派生:A08,A07｜<选项中文>｜置信度约N%｜机制：<第1步那句话>；<反证及取舍，没有就不写>"]}
```

- 只交一个编码：不交数组、拼接值、中文整句。
- 最高一项置信度不过半才 skip R10，并在依据里写最接近的两项及各自置信度、具体缺口。

## 业务线索门禁

build 输出 `CHECK CATEGORY_SIGNAL <键>｜…线索…` 时不得调用 mcp_run_process，二选一：

1. 线索成立：回到第 2 步，set 线索对应（或你判断更准确的另一个特殊类）选项；
2. 线索是误报（第 3 步反例）：在 build 的 stdin 写 `"categoryReview":{"<键>":"为什么不构成该类业务，引用原文用「」，至少 10 字"}`，理由进 notes.toolIssues 供人工复核。

线索只是词表命中，脚本不替你定值；没有线索也不代表一般业务，仍按四步判定。

## 用工场景与经营范围分别判断

用工场景看本次人员实际从事的业务；经营范围类目看登记范围原文。不同维度编码不互换，某维度缺选项不影响其他维度提交。

| 本次人员实际从事 | 用工场景选项含义 | 经营范围类目含义（登记范围有对应证据时） |
|---|---|---|
| 药品、医疗器械销售或医药推广 | 医药 | 医药及医疗器械销售 |
| 直播介绍商品、促销并引导下单 | 直播带货（普通直播另选直播） | 电商直播带货 |
| 影视拍摄、制作与业务执行 | 影视 | 影视传媒 |
| 律所法律咨询、诉讼代理 | 律所 | 律师及会计师事务所 |
| 会计师事务所审计、专业会计服务 | 会计 | 律师及会计师事务所 |
| 保险产品销售、保险经纪或代理 | 保险经纪 | 保险经纪代理 |
