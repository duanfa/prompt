# admission-noshell-v0-2 / admission-v0-2-materials

# 材料盘点与直取

按属性含义匹配请求字段、材料和工商，不按旧对象名硬套。

## 第一步：附件状态（fill 的 materials）

init 已写好“未提供 / 仅URL / URL 失效”（URL 失效的同时进 notes.unreadMaterials，明细 N 条目用 R01）。对 init 列出的每个待填附件字段给状态：

- **可读**：图片块、PDF 文件块能看到内容；依据 = 原件上一个真实栏位的短原文（PDF 加页码）。**标“可读”就必须给出能核对的原文栏位**，没看清不标。
- **不可读**：当前确实只有占位文字、无法查看；依据写具体原因（记 unreadMaterials）。不可读材料不猜正文，不借用申报/执照名称填开户户名。

判断以实际能看到的内容为准（红线 1）：日志里的 `[unknown]` 是 PDF 的展示降级，扫描 PDF 无文字层也可视觉阅读。没有路径的图文不调用 Read/Glob，也不因找不到文件记“未提供”。与本次目标无关的材料注明“与目标无关”，不必精读。

## 第二步：只对“可读”材料取栏位（按 init 打印的待填行逐条取，规则没引用的栏位也取）

**营业执照颜色观察与复核（B12，提交 fill 前完成）**：

1. 回看本次 `bizlicUrl` 对应的图片，分别观察证件底色、文字和边框、印章、其他图案；先记录各区域实际可见的颜色，再给出布尔值。来源写材料字段和位置，证据写观察结果。观察不到的区域写“无法辨认”，不按证件通常的配色补全，也不借用其他附件的颜色。
2. 证件区域完整可见且只有黑、白、灰，B12 必须为 false，灰色印章也属于灰色；清晰可见其他色相才能为 true，并指出具体位置和实际颜色。材料可读但颜色无法分辨时填 null、R06；明确看清全为黑白灰时直接填 false，不记为未知。RGB 格式、有印章、文字清晰均不是彩色依据。
3. 准备提交 true 时，针对所声称的有色部位回看原图一次。例如证据写“印章红色”，就回看那枚章，确认实际可见红色；章的形状、印文和登记机关名称不能证明它是红色。复看为灰色且其余区域也只有黑白灰，改为 false；仍无法分辨，改为 null、R06。复核读取原图，不沿用首次描述作为证据；本步骤不调用仅用于工商差异的 `detail.py recheck`，只提交复核后的 fill 行。
4. 颜色、公司章、登记机关章分别判断。灰色登记机关章可使 B27=true，同时 B12=false；有灰色章不能据此确认有鲜章，也不能改变 B13 的公司章口径。颜色判断不证明原件或真实性。

黑白灰反例（仅示格式，实际颜色须回看本次图片）：

```json
["B12","false","营业执照 bizlicUrl 整页｜白底，文字及边框为黑灰色，右下登记机关章为灰色；整张证件仅见黑白灰"]
```

**章的内容**（所有「…章内容 / 章载名称」类条目，当前为 G11）：先读印文原文，再判断这枚章是不是申报企业的章——印文去掉末尾「合同专用章/财务专用章/业务专用章/发票专用章/公章/专用章」等字样后，主体名称与营业执照名称 B01 一致（只差空格、括号全半角也算一致），就是该企业的章。**是该企业的章：value 填企业名称 A02 原文**（一字不改，不带“合同专用章”等字样），证据写「印文原文：××合同专用章｜去掉专用章字样后与执照名称一致」；**主体名称不同**（简称、缺字、多字、别家公司，如执照「北京某某科技有限公司」、章「某某科技 合同专用章」）**value 照抄印文原文**，证据写哪里不同；没有章或看不清记 null R03/R06。不要因为“像是同一家”就填企业名称。

## 第二步半：与工商比对，不一致先回看原件

fill 提交后，脚本把原件识别值与工商返回**逐项比对（12 项）**：营业执照 B01/B03/B06/B04/B05/B07/B08 对工商 J01/J02/J07/J09/J10/J13/J16（即 J34 的七项）；身份证姓名 C02、开户凭证法定代表人 D08 对 J07；开户凭证户名 D01、租赁合同承租方 G02 对 J01；执照注册资本 B10 对 J08（工商没写单位时不比）（后五项只进 conflicts，不进 J34）。**任一侧没有值不比较。**不一致的项以 `RECHECK_ITEM 条目ID|说明|首次识别=…|首次来源=…|工商 Jxx=…` 列出。对每一项：

1. 回到原件（图片看对应那张，PDF 看“首次来源”里的页码），**只重看该栏位**，按原文重新识别一次；不因工商值而改写原文，也不沿用首次的值。
2. 用 `detail.py recheck` 提交：`[条目ID, 二次识别值, "来源｜二次识别时原件栏位原文"]`；仍无法确认就写 `[条目ID, null, "Rxx｜具体原因"]`。
3. 脚本判定：二次与首次相同 → **确认不一致**，保留原件识别值，source 追加复核记录，J34 与 conflicts 标「已二次识别确认」；二次与首次不同、与工商一致 → 首次识别有误，**更正**；二次与首次不同、与工商也不符 → **两次识别不一致**，置 N R06 不取值；**无法确认** → 置 N 不取值。
4. **工商值永远不覆盖原件识别值**：原件上写的是什么就记什么，两者不同就如实进 conflicts，不裁决真假。
5. **每项只复核一次**；没处理的 RECHECK_ITEM 会让 fill 不出 PASS、`combine.py build` 被拒。改了原件或工商侧的条目，之前的复核结论作废，需重新比对。

复核的是“识别准不准”，不是真伪：确认不一致不等于伪造，不据此填伪造嫌疑类条目，也不据此填任何“真实/已核实”属性。
