# job 216：脚本止损与平台防循环接入

## 本地已经实现

`detail.py` 对 fill/recheck 的 stdin 做一项有限恢复：最后一行三元组已经闭合，但 rows 数组与下一顶层 notes/materials 之间缺一个 `]` 时，检查补一个括号后全文可解析、顶层仅含 rows/materials/notes、没有重名键、所有已解析值保持不变，才继续执行并打印 `WARN STDIN_ROWS_CLOSED`。其他损坏仍拒绝，不猜测或改写证据。

拒绝返回稳定标识 `STDIN_JSON_INVALID`，报错偏移仅供定位。主提示词和 catalog skill 规定只纠正结构或按材料拆成每批不超过 20 行；同一步骤连续第二次语法失败时提交审核未完成，不进入引擎。这个次数限制目前是模型行为约束，尚未在 WanScope 控制器实施硬终止。

## 平台需要实现：由程序序列化 stdin

当前 `RunSkillScript.input_schema.properties.stdin` 是字符串；模型需要在工具参数 JSON 里再手写一份转义 JSON。外层合法并不保证内层合法，job 216 正是这个问题。

建议增加可选参数 `stdin_json`（JSON object），与旧的 `stdin` 字符串互斥；平台先校验对象，再用 `json.dumps(..., ensure_ascii=False)` 生成进程 stdin。保持旧参数兼容，更新工具 schema 和描述后再让主提示词切换。不能只让模型传未转义对象而不修改工具契约。更强的专用提交工具可把每行声明为带 id/value/text 字段的对象，平台再转换为脚本三元组。

本次仅修改技能包，未修改或部署平台工具。

## 平台需要实现：按步骤识别没有进展的重复失败

建议在工具执行结束后、发起下一次模型调用之前检查：

1. 状态按会话/requestId、脚本、子命令归组，如 `detail.py/fill`。语法失败统一记 `STDIN_JSON_INVALID`，忽略行号、字符偏移和附近的证据文字，避免模型改两个字就绕过识别。
2. 同一步骤连续两次同类失败且没有成功写入时，控制器结束当前自动执行，保存失败步骤和错误，生成“审核未完成：提取数据提交失败，规则引擎未执行。”。退出码只会产生一条工具结果，必须由控制器实际终止循环；再给模型一句“不要重试”不能保证结束。
3. 只有成功写入、待填减少、复核项减少、门禁阶段推进等可观测变化才算进展。工具入参 hash 变化或解释文字变化不算；正常的分批写入和后续待填提示不算失败。
4. 失败收尾不生成通过/拦截结论，不调用规则引擎。仅按失败契约保留已确认的标识、错误信息及历史文件。总步骤数/总耗时上限再兜底，不能代替步骤级识别。

建议运行时发出结构化错误类别/进展字段；兼容旧脚本时可以暂时匹配 `stdin 不是合法 JSON`。本地只读重放结果在 `artifacts/ontology-job-216-loop-20261110/`；这不是平台熔断或远端业务全流程的验证。
