# admission-noshell-v0-1 / admission-v0-1-facts

# 事实汇总与派生

只用本次已取得的定义、请求事实、**可读**材料、视频问答和工商返回；不重复取证。每个规则引用键须有去向：取值＋来源证据 / 来源不可读 / 口径不足（对不上清单条目或无本流程口径）/ 定义矛盾。**没有明确依据的属性一律不填，skip 是预期结果，不以减少 skip 为目标补猜。**

## 原文与类型

- 名称取指定原件栏位，逐字、不纠错、不用 entpName 或工商名称替代。成立日取执照“成立日期”，不用发证日；营业期限“长期/永久”不造截止日，严禁用成立日加年数推算。
- 布尔有明确依据才填；读取成功且范围足以确认不存在时可 false；没提到、读不了、无法判断不传。计数为 0 仅在清单完整且确认没有时才是事实。
- 枚举按红线 5 从选项里选：有 `enum` 选 enum 编码，没有 enum 选 comment 列出的选项；**整句话、选项以外的相似代码一律不填**。NOT IN 里的集合只是条件常量，不能证明其他取值的正向分类。
- 原文型任务/项目/交付要求保留对应字段原文，不改写、不用企业名称代替；**仅当该键被规则引用才放进 input**。
- “已完成核验”与“内容匹配”分别取证，不互相改写。全0、全1、XXXX 等占位内容不当真实事实；“测试专用”水印不影响可读栏位摘录。

## 属性填写原则（不点名任何具体规则或属性）

规则和本体属性每次由 mcp_list_rule / mcp_list_property 返回，会经常变，本 skill **不维护“哪些属性可填”的名单**。对本次规则引用的每个键，按下面的原则逐个判断；判断依据永远是本次的规则条件、属性 label/comment 和清单条目的 name/desc。

1. **固定标识**：A01–A04 直接取请求参数，对应属性已预设，build 自动传入，不用你映射（见 discover skill“标识”）。
2. **有清单条目支撑才填**：键按语义对得上某个清单条目、该条目有值（Y）、并且规则条件的含义与条目含义一致，才填；对不上任何条目的键不填，登记 `unfilled`。清单条目自带的口径（见各条 desc）优先于任何推断。**含义不同的条目不能互相顶替**；原始描述不是分类枚举的编码，不能直接映射到分类属性。
3. **请求原文型字段**（任务、交付要求、项目内容、开票类目等）：仅当规则引用该键，取请求字段原文，不改写。
4. **综合判断的属性**：根据当次 label/comment、规则条件及材料判断，列全支持和反对该结论的证据。合格、完整、一致等综合结论不能由单一有利特征代替；已有明确反证时不能仍判合格。影像合格应综合清晰、形式要求及伪造嫌疑，彩色、有章不能抵消明确的伪造嫌疑；未见嫌疑不等于证件真实或持证人已核实。依据不足不填；已有证据足以明确否定时，可据该反证给出否定值并说明。属性名称、含义或清单编号变化后重新按含义选择依据，不沿用旧映射。
5. **true / false**：有明确依据才 true；材料已读成功、范围足以覆盖、明确确认不存在才 false；没看到、读不了、判断不确定一律不填，不用 false 顶替。
6. **比较类**：两侧指定原文都可读才比较，evidence 并列两侧原文；任一侧不可读则省略。一种材料的事实不代表另一种材料。
7. **关键词类**：本次规则明确给出完整关键词表，才按目标原文逐词核对，未命中才 false；没有词表不填。
8. **没有本流程口径的判断类一律不填（执照/身份证影像合格属性有口径，见“营业执照、法人身份证的影像要求”，不适用本条；属性定义自带选项的枚举——有 `enum`，或 comment 写了「枚举 X：选项…」——也不适用本条，按红线 5 当选择题选，见下面“枚举选项即口径”），更不得填 false**：牌照/资质/许可、行业禁入/灰名单/敏感场景、业务分类、付款方/关联任务/实际业务是否相符这类需要实际业务核查或外部来源的判断。自报不是核实；工商核准范围不等于实际业务；“除依法须经批准的项目外…”是通用套话，不当证据。清单条目自己给出了人工核对口径的（见其 desc），规则引用对应属性且条目有值时按条目填，口径之外的判断仍不填。
   **枚举选项即口径**：定义给出了选项（含“一般行业”这类兜底项），且请求里有可读的对应原文（项目内容、交付要求、开票类目、经营范围等），就是有口径的选择题：逐项估计把握，最高一项过半就 set 提交该选项，依据写原文。不得以“行业分类/业务分类需业务判断”整体 skip。plan 对键打印 `EMPTY_GATE` 时，skip 会让“为空即拦截/转人工”的规则直接命中——更要先按选择题判断，确实无依据（原文全空、或各选项都不过半）才 skip。
9. **结果类**（引擎产出的结论、处置、风险等级、命中标志等）永远不填。
10. **视频类判断**（场所真实/虚构/已核实等）见 video skill：推测措辞不是证据。
11. **定义含义与规则用法对不上**时不填，记 toolIssues（红线 4），不硬映射、不用相似代码凑。

## 派生口径

1. **比较**：两侧指定原文均可读才比较，evidence 并列两侧原文。未定义归一化时仅忽略空白和括号全半角，其余差异均视为不同。两侧 input 已有值时比较结果须一致；任一侧被排除，派生值也排除。
2. **日期比较**：build 把日期键统一成 8 位 yyyyMMdd（到期类取截止日，“长期/永久”不传）；一侧缺失不补另一侧。
3. **成立月数（B16）等完整月数由脚本算**（（基准年−成立年）×12+（基准月−成立月），基准日的日小于成立日的日再减 1）：基准日优先业务申请日，其次 taskSubmittedDate，再次当前北京时间；非业务申请日时 toolIssues 记回退来源；日期不明不填 0，成立日晚于基准日记冲突。
4. **枚举/分类映射**：属性定义确指该含义时，按红线 5 当选择题从选项里选一项（置信度过半才选）；不要求规则条件里出现该编码（红线 4、5）。

### 一般行业兜底

- 定义的可选项包含“一般行业”时，先依据项目内容、交付要求、开票类目、经营范围及实际业务材料判断特殊类别：金融类、传销类、违法类、高危类、同业类、敏感类、音视频制作。业务内容可辨识、未命中上述类别且“一般行业”的把握超过 50%，选择“一般行业”；不要求申报人逐字填写“一般行业”，不因“分类需要业务判断”整体 skip。
- 所属行业、实际业务类别、用工场景分别按本次定义判断。证据支持它们同属一般行业时，三个规则引用键都提交 map/set，不能只填前两个而遗漏用工场景。依据列出项目及相关材料的清单条目，写「派生:依据条目ID｜一般行业｜置信度约N%｜可辨识的业务内容及未命中特殊类别的理由」。有 enum 用本次编码，没有 enum 用 comment 的选项文字；不固定猜测英文编码。
- 不能只因某条违法类规则未命中或被跳过就选择一般行业。业务内容空缺、材料不可读、存在特殊类别证据、来源冲突或分类仍不确定时不兜底，按实际原因保留未知；企业所属行业与本次岗位的用工场景不同，分别判断。
- **组装补漏**：`combine.py build` 在两个来源分类均已按本次定义确认为一般行业、全部依据有值、目标有定义且被有效规则引用，并且模型尚未对用工场景提交 map/skip/set 时，沿用两者证据补齐用工场景，打印 `GENERAL_INDUSTRY_FALLBACK`。目标按自身 enum 编码；不覆盖显式取值、skip 或待判断映射，不复用上次 build 的分类值。配置在 `combine_config.json` 的 `generalIndustryFallback`。

## 冲突

先核对名称/信用代码，不合并不同主体。同一主体的影像/工商事实可优先于单方自述；同级冲突无法裁定时，冲突属性及依赖它的派生值一并省略，conflicts 记双方原文与材料名。“招牌不同”不升级成“无关联/冒用/虚构”。修订只处理具体错误，不为润色重写正确事实。

## 两个落盘文件：由脚本生成

调用方式见主提示词第二节。本 skill 管的是**你读材料后提交的那部分行怎么取值**，以及哪些属性需要你判断后用 `set` 提交。

### 阶段 1：detail.py init → fill

1. **init 的输出列出你要填的行（id｜name｜desc）**：每条的取值与判定口径看它自己的 `desc`（人工核对清单原文），不要凭记忆。原文型事实（B01–B08、B10、B20、B21、C02/C03、C13/C14、D01/D02、D07–D11、G02–G04、G10、H02/H03、H05、H07–H09 等）读到就取，**不受规则是否引用限制**。
2. **派生条目由脚本算，你不提交**：B11、B15–B19、B22、B24–B26、D04、G05、G07、J32–J36、A12、F01 等（重交会被跳过，打印 `SKIP`），每次 fill/recheck 后按当前依据重算并重建它加的冲突说明；依赖行为 N 时脚本写 `N｜R12｜缺 <ID>`。你提交的是依赖的原文行。
3. **营业执照、法人身份证的影像要求**：按当前清单 desc 逐项提取彩色、鲜章、清晰、伪造嫌疑等事实。影像形式应为彩色，或非彩色但可见鲜章；身份证正反面分别看，文字清晰、正反面齐全或有效期正常不能替代形式要求。影像合格还须完成伪造嫌疑检查，明确有嫌疑时判不合格，彩色或鲜章不能抵消；无法判断时不得判合格。映射到何种本体属性、布尔取值的方向以及需要哪些依据，由你结合当次属性定义和规则判断，脚本不按这些条目的历史编号固定计算。
4. **需要读图判断的行**（B12–B14 彩色/公司鲜章/清晰、B27 登记机关的章、D05/D06、F02–F06、G01/G06/G09/G11、H01、社保/完税/无欠税证明的「是否提供」条等）按它们的 desc 取。**“是否有伪造嫌疑”类条目**（B23、C10、D12、F06、G08、H11、H15、H18、H21）：true 只在能指出具体可见异常时填，false 只表示已逐项看过未发现异常，二者都不是“真实/已核实”的依据；伪造嫌疑条目可作为影像合格的必要检查项，按本次含义与其他事实综合判断，不得据此推出真实/已核实类属性的 true；拿不准 N R06。**text 只写逐项看了什么**，**不得出现“真实/合规/正常/可信/无异常”字样**（“格式合规”“国内真实地址”“显示正常”也算；有值的行里含这些字的分句脚本会去掉，打印 `TRIMMED`；**每一句都含这些字时整行退回**，照退回意见改写，不要原样重交，连续 3 次仍这样脚本记 null R06，打印 `ASSERT_FALLBACK`）。拿不准的疑点写成具体现象，不在别处下“伪造”结论。**“快到期提醒”类**阈值暂定 30 天（脚本已按此算）。
5. **你自己写的「派生:…」行**脚本不重算：依据行的值变了，fill/recheck 输出 `STALE …`，按新依据重判后 `fill --force` 重提；STALE 未清，fill 不出 PASS，build 被拒。
6. fill 打印 PASS 后明细已包含清单全部条目，不需要回读。

### 阶段 2：combine.py build

1. 脚本自动写 `refKeys`、entities、rules 原文副本、unfilled、notFoundInDefinition、`rulesDropped`，并跑 validate（含键数闭合）；你不手写任何 combine 内容，也不做键数自审。
2. **由你判断规则范围**：按当次规则含义、适用阶段和证据判断；明确与客户准入无关的用 `rules.drop` 提交原因，需恢复用 `rules.keep`。脚本只执行显式决定；未明确排除的规则保留，不因属性改名或无默认映射被自动抛掉。
3. **由你决定属性映射和取值**：先运行 `combine.py plan`，逐个看当次属性 label/comment、规则条件与清单条目的 name/desc。原文或已提取的同义事实用 map；业务判断、枚举转码、多个事实综合判断用 map 列全部依据，并用 set 提交值与推导；依据不足用 skip。脚本不维护业务属性默认表，不按属性名、旧编号、标签关键词替你计算合格、状态或分类；唯一的分类补漏是上文“一般行业兜底”，只沿用已有一致判断和证据。map/skip 只在本次请求内复用。
4. **set 提交判断结果**：无论一个还是多个依据条目，只要取值需要理解业务含义，就用 set 提交 `[值,"派生:依据条目ID列表｜各条目事实与推导"]`；map 与来源必须列出相同的全部依据，依据缺失不填。多条 map 未提供 set 时打印 NEED_VALUE。**set 不落盘，每次重跑 build 都要重新根据当前事实提交。**
5. **UNDECIDED**：规则引用了、你既没 map 也没 skip 的键，脚本按 R10 记入 unfilled 并列出（带 label）；逐个按 discover skill 第 6 条改放 map 或 skip 的对应码，确实无口径的保持 R10。**IGNORED**：你提交了但不是规则引用、也不是标识的键，不进 input。
6. **枚举键**（定义带 `enum`，或 comment 以“枚举”开头）按红线 5 选一项：有 enum 交 enum 编码，没有 enum 交 comment 选项原文；不是布尔或整句话，不符 build 打印 `ENUM_DROPPED` 并按 R10 记入 unfilled。置信度不过半而 skip 的，摘要不要说成“申报为空”（result 阶段会提示哪些命中规则涉及未传入引擎的属性）。**类型也按规则用法核对**：规则只拿它和 true/false 比的键只收布尔、只和数字比的键只收数字，文字（经营范围、招牌原文、附件盘点）映射过去 build 打印 `TYPE_DROPPED` 并不传——这说明映射的条目含义对不上，改映射或 skip；日期键由 build 统一成 yyyyMMdd，“长期”不传。定义含义与规则用法对不上的放 `skip.R11`，并在 `toolIssues` 写“键｜定义含义｜与规则用法冲突，未映射”。

#### value 转型（供 set 提交与核对用）

`"true"`/`"false"` → 布尔；条件里该键只与数字字面量比较 → 数值；标识类（A01–A04，脚本自动保持字符串）与原文型字段 → 字符串；枚举键交选项（有 enum 交编码，没有 enum 交 comment 选项），不是选项则不提交。

### 之后的修改

- 改一个事实：`detail.py fill --rid <id> --force`，stdin 里只放要改的行，再重跑 `combine.py build`（带上 set）。不直接编辑任一文件。
- build 打印 `CHECK`：按提示用 `fill --force` 改写被点名的行（只写逐项看了什么），再重跑 build；拿不准就改为 `[id, null, "R06｜…"]`。
- 引擎调用之后，不再运行 fill/build（提交后文件保留，作为参数来源台账）。
