# 台账与摘要终结器接入（v30-claude）

沿用 v20-codex 的方案：**文件负责留痕，程序负责计数和校验**。模型只写分组短句并关联真实规则 ID；统计、覆盖、方向、依据、来源一致性由程序保证。本目录是已离线测试的参考实现，**尚未注册工具、未接入服务、未部署**；只安装 Skill 不等于程序校验已生效。

## 相对 v20-codex 的扩展：`basis`（依据）

v19c 实测：32 条明确结果里有 **13 条 false 的 reason 是“属性/对象不存在”**（`AdmissionDoc.doc_type` 缺失等），即条件根本没求值，模型却把它们写成“账户性质合规”“营业执照在有效期内”等已满足事实。仅靠 ID 覆盖校验拦不住这种语义错误，所以台账增加：

- 每条规则带 `insufficient`：`result=false` 且 reason 匹配“(属性|对象)不存在”。
- 草稿 group 增加 `basis`：`determined`（默认）或 `insufficient`。程序要求同组规则的依据与台账一致，否则 `WRONG_BASIS`；true 永远是 determined。
- 渲染时 insufficient 的组固定输出为“未触发（所需属性未取得，未据此核实）：…”，首句附“其中 x 条因所需属性未取得而未触发、未据此核实”，x 由程序计算。
- 统计增加 `falseInsufficient`。

v26 起 `is_insufficient(state, reason, expression)` 按表达式结构判：最外层只有 AND 且 reason 含“不满足 …” → 该条已求值（determined），例如 `RULE-IND-PRO-001`（`name_blacklist_hit=false` 已确定，`task_category` 属性不存在）、`founded_months=23` 下的 `RULE-ADM-003`；单个条件、最外层含 OR 或 AND/OR 混合、reason 只有“不存在” → 仍为 insufficient（偏保守）。不传 expression 的老调用方式保持旧口径。

这样“没求值”不再依赖模型是否记得加“未据此核实”，而是结构上无法写成“已满足”。仍不能证明中文短句本身准确。

## 四份文件各由谁写

每次引擎尝试使用独立调用 ID 目录，例如 `work/<requestId>/engine/<callId>/`；只有服务端确认的最后一次成功调用能终结摘要。

| 文件 | 写入方 | 内容 |
|---|---|---|
| engine-response.json | 引擎工具包装层 | 截断前的完整返回原文，关联 request 及 input 快照 |
| rule-ledger.json | 程序 | 调用 ID、输入/结果哈希、total/determined/true/false/skip/falseInsufficient、逐条规则（result、category、insufficient） |
| summary-draft.json | 模型 | 仅 groups（category、result、basis、ruleIds、text）；不手填统计 |
| summary-validation.json | 程序 | 校验结果、快照/草稿哈希；最终两个摘要由程序同源渲染 |

落盘用同目录临时文件后原子替换。原始结果和台账对模型只读；文件句柄/路径必须归属当前 request，不能仅信模型提交的路径或哈希。多次引擎调用不覆盖旧记录。

## 接在哪里

1. `mcp_run_process` 的实际工具包装层，在 SDK/日志截断前捕获完整 ToolResponse，存原文与 input 快照。日志里的 65,536 字符预览不能当完整结果。
2. 服务端调 `build_ledger(response, engine_call_id=..., request_id=..., input_snapshot=..., complete=True)`；`complete` 来自真实传输状态。未知 result、重复 ID、非完整列表直接失败，不悄悄丢弃。
3. 引擎返回附一段台账引用及统计（含 insufficient 标记），减少模型处理长返回。
4. 注册只读业务结果、只写摘要产物的 `FinalizeRuleSummary`，参数仅 `ledgerRef` 与 `draftPath`；服务端从自己保留的原始返回重建台账再 `finalize(...)`，不接受模型上传的 response。草稿错时返回差异，不重跑引擎。
5. 最终结构化提交的 mapper 再绑定最后成功调用与同一 input 快照，用通过校验的渲染结果覆盖 `summary`、`summary_debug`；无通过的终结产物则拒绝“完整摘要”。`category_by_rule` 由服务端按业务元数据维护，缺省为“其他”。

## 校验边界

`rule_ledger.py` 是标准库纯函数，无网络/模型调用。能保证：数值、ID 覆盖且恰好一次、方向、类别、依据、来源一致性、snapshot 一致、两份摘要同源（去掉来源标记后逐字相同）、public 文本不含 ruleId。不能保证：中文短句语义、上游事实真实、AND/OR 短路的解释。

## 验证

- 离线测试：`python3 -m unittest discover -s integration -v`（5 项原有契约 + 4 项依据测试，共 9 项通过）。运行时 Agent 不执行该命令。
- 对 v19c 真实返回回放：199 条 = 7 true + 25 false + 167 skip；明确结果 32；其中 13 条 false 为“属性不存在”；模型写的 24（7/17）被判定错误，漏 `RULE-ADM-006`；故意移除该 ID 时程序拒绝 `MISSING_RULE_IDS`。见 `analysis/v19c/`。
